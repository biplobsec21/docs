System overview

This database is organized by business domain and designed to support the TukTakKaj marketplace, including user identity, task posting, bidding, payments, finance, trust, support, and reporting.

134 Tables
1617 Fields
14 Schemas
PostgreSQL 15+

Key conventions

The data model follows a consistent naming and lifecycle pattern across the platform:

  • id = internal database key
  • public_id = UUID used in APIs
  • created_at / updated_at = timestamp tracking
  • deleted_at = soft delete marker
  • version = optimistic locking counter
  • *_enc and *_hash = encrypted and hashed sensitive fields
  • Money is stored in BDT with 2 decimal places

Delivery category setup

Delivery is the parent category; Goods and Documents are selectable leaf categories. Both leaves require pickup and drop-off locations and have a minimum TukTaker age of 18.

  • item_description textarea — required on Delivery; form validation config sets a 5-character minimum
  • approx_weight_kg number — required for Goods; form validation config sets a 0.1 kg minimum
  • is_fragile boolean and declared_value_bdt number — optional Goods details
  • document_type select — required for Documents; letter, contract, certificate, bank/legal, or other
  • signature_required boolean — optional Documents delivery instruction
  • Form answers are stored in task.tasks.attributes; the database checks required answers on publish, while configured value constraints are validated by the application.
  • Publish flow: create as draft, add pickup and drop-off rows, then publish. Direct insertion as open is rejected.

Category search configuration

Seed data supplies English, Banglish, and Bangla keywords and synonym mappings for category search, including delivery terms such as courier, parcel, package, and কুরিয়ার.

Tables: catalog.categories.search_keywords, catalog.categories.search_vector, catalog.search_synonyms

Design principles

The schema is intentionally structured around secure identity, financial correctness, auditability, and clear lifecycle tracking. Sensitive user data is encrypted or hashed; every major money movement is journaled through the ledger; and each workflow keeps history instead of overwriting it.
